# v1.0 release criteria

v1.0 means a user can trust what scitq reports without checking behind it,
and can rely on its interfaces not breaking without notice. Each item below
carries the condition that marks it done.

The current 0.10.x work (definitive failures, leaf-step workflow success,
template folders, recovery-path exit codes, missing output directory,
recruiter rank ordering) ships first, as its own release.

## 1. Per-task output manifest

S guarantees two things: the program itself exited 0, and every file it
left in `/output` reached the destination. Whether that set is empty is the
program's business; scitq records it and reports it.

- At task end the worker records the files and bytes present in `/output`.
- After upload it checks the destination holds the same names and sizes.
  A shortfall is a scitq fault: the task is F with class `network` and is
  retried.
- The counts are stored with the task and shown in `task list`, the UI and
  MCP.

**Done when:** a task's produced and uploaded file counts are visible in
all three surfaces, and an integration test that drops a file between
production and upload ends in F.

**Status:** done. Columns `task.produced_files`, `produced_bytes`,
`uploaded_files` (migration 55); per-file size check after each copy;
tests in `client/uploader_test.go` and
`tests/integration/output_manifest_test.go` (an unwritable destination
ends in F with the shortfall recorded).

## 2. Audit trail

Every change to a worker's assignment, a task's fields or status, or a
workflow's status records what changed, when, and who made it: user,
agent token, or recruiter. Recycling decisions are recorded the same way,
not only in the server log.

**Done when:** for any worker, scitq answers "why is this worker on this
step, and who or what put it there" from its own data.

**Status:** done. Table `audit_event` (migration 56); recording helper in
`server/audit`; `scitq audit list|prune`, MCP `list_audit`. Scope:
decisions only — task status transitions reported by workers are not
recorded. Agents are identified as their user plus the MCP client name;
telling apart two agents of the same user needs one account per agent.
Tested in `TestRecruitmentCycle` (deploy and recycle by the recruiter,
then an update via MCP, each with its actor) and `server/audit_actor_test.go`.

## 3. Stable, versioned interfaces

v1.0 promises stability for the gRPC API, the YAML template format, the
Python DSL, the MCP tool names and the CLI flags.

- A written compatibility and deprecation policy.
- Defined behaviour when server, workers and CLI run different versions.
- A tested upgrade path from the previous release.

**Done when:** the policy is published in the docs, and CI upgrades a
server running the previous release, with its workers, to the candidate.

**Status:** done. Policy in `docs/reference/compatibility.md` (semantic
versioning; a server supports workers and CLIs down to the previous minor
release; deprecated surface works until the next major). CI job `compat`
runs `make compat`: `buf breaking` on the proto (WIRE_JSON), recorded
surfaces `compat/{cli,mcp,python,config}.txt` that must match the code and
may only grow since the last release, and the template `format` check. CI
job `test-upgrade` runs `tests/upgrade/run.sh` (v0.10.1 → candidate: server
switch mid-workflow through the graceful gate, migrations under a live
worker, then an in-place worker upgrade); verified locally on darwin/arm64
and emulated linux/amd64. CI job `unit` now also runs the Go unit tests and
the Python suite, which no CI job ran before.

## 4. Recruitment rules written down and enforced

Every recruiting rule is a rule for the step as a whole: `max_workers`
counts all workers on the step, and `rounds` sets the step's target. Ranks
only order the sources of workers. A rank acts once every lower rank is
done: the step reached that rank's `max_workers`, or the rank has nothing
it can recycle or deploy. A rank's timeout gates cloud deploys only, and
starts when the rank becomes eligible; recycling never waits.

- A docs page states these rules.
- A step's recruiters must agree on `rounds`; recruiter creation rejects a
  disagreement.

**Done when:** the page is published and creating disagreeing recruiters
fails with a message that names the step and the conflicting values.

## 5. Failure classification

A Docker daemon restart kills containers with exit 137, which today is
filed as `oom`, so retries escalate memory for nothing. OOM is reported as
`oom` only when the container's `OOMKilled` flag is set.

**Done when:** a test restarting the daemon under a running task yields a
non-`oom` class, and a test exceeding the memory limit yields `oom`.

## 6. Security review

Review and decide on: token lifetime and revocation, the privileges the MCP
server exercises on behalf of its logged-in user, and `scitq_auth` tasks
reusing the worker's own token.

**Done when:** each topic has a recorded decision, and the changes it
calls for are shipped.

## 7. UI live updates without flicker

A value shown in the UI changes only when the underlying data changes. Each
displayed value has one source of truth; WebSocket deltas merge into the
existing row and never replace it with a partial one.

**Done when:** every reported blinking element is fixed, and each fix has a
component test that feeds a sequence of WebSocket messages and checks the
displayed text never takes a wrong or empty intermediate value.

## 8. Operator docs

A concepts page (task lifecycle, retries, definitive failures, workflow
success, recruitment), an upgrade guide, and a CHANGELOG maintained from
this release on.

**Done when:** all three are published in the mkdocs site.

## 9. Small items from `specs/todo.md`

The UI force-run button for waiting tasks, and pair-aware fastq iteration.

**Done when:** both are shipped or explicitly moved past v1.0.

## Out of scope for v1.0

New cloud providers, Nextflow/Snakemake import improvements, and anything
else marked as future work in `specs/`. Each would enlarge the surface v1.0
commits to keep stable.
